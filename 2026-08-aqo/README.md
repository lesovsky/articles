# aqo: материалы исследования

Полный набор данных и скриптов к исследованию расширения `aqo` (Adaptive Query
Optimization) в Postgres Pro Enterprise.

## Статус: статьи не будет

Исследование доведено до конца и дало ясный ответ, но материал в публикацию не
пошёл: инструмент оказался слишком узконаправленным, и искать под него аудиторию
нецелесообразно. Замеры воспроизводимы, методика описана — если появится повод
вернуться к теме, всё лежит здесь.

## Вопрос эксперимента

Имеет ли `aqo` практическую пользу для DBA: в каких сценариях он даёт прирост,
по каким признакам это можно понять заранее и как измерить эффект до и после
внедрения.

## Короткий ответ

**Выигрыш появляется только там, где исправление оценки переворачивает форму
плана.** Величина ошибки оценки не предсказывает ничего.

Итоговая серия на верной стоимостной модели, три чередующихся раунда:

| запрос | base | aqo | дельта | разброс | ошибка base → aqo | форма плана |
|---|---:|---:|---:|---:|---|---|
| **q5** цепочка из 5 join | 1058.6 | **731.9** | **−30.9 %** | 7.9 % | 33.1x → 2.4x | **сменилась** |
| q4 предикаты по выражениям | 3667.4 | 3678.9 | +0.3 % | 3.8 % | **286.7x → 1.2x** | та же |
| q2 корреляция через join | 1953.7 | 1922.7 | −1.6 % | 6.8 % | **24.3x → 1.6x** | та же |
| q6 число групп | 5505.9 | 5395.4 | −2.0 % | 6.0 % | 1.6x → 1.6x | та же |
| q1 корреляция в таблице | 1486.1 | 1458.4 | −1.9 % | 10.5 % | 1.6x → 1.6x | та же |
| q3-hot перекос, частое значение | 40.2 | 37.3 | −7.1 % | 9.3 % | 17.9x → 17.9x | та же |
| q8 комбинированный | 1551.3 | 1592.9 | +2.7 % | 1.9 % | 2.9x → 2.9x | та же |
| q7 OLTP | 9.2 | 9.5 | +3.4 % | 8.8 % | 5.1x → 5.1x | та же |
| q3-cold перекос, редкое значение | 1.8 | 2.2 | +23.6 % | 25.9 % | 9.8x → **16.1x** | та же |

Один запрос из девяти. У `q4` ошибка оценки упала в 240 раз и дала +0.3 % времени.

## Что это значит для DBA

**Пробовать стоит** на многотабличных аналитических запросах от четырёх-пяти
соединений, где у планировщика есть выбор порядка и способа join, и где
корреляции не лечатся расширенной статистикой — корреляция через join, предикаты
по выражениям.

**Не поможет**, если плохой план вызван стоимостной моделью, а не кардинальностью.
Проверяется до внедрения: если оценки в `EXPLAIN ANALYZE` уже близки к факту, а
план плох — дело не в `aqo`. На `q1` расширение довело оценку до идеала и не
изменило ничего, а правка `random_page_cost` с 1.1 до 4 ускорила тот же запрос
на холодном кеше в 6.3 раза: 505 с → 80 с.

**Не нужен** там, где справляется `CREATE STATISTICS` — корреляция внутри одной
таблицы и число групп в `GROUP BY`. Это дешевле и предсказуемее: без обучения,
без оверхеда, без нового состояния в кластере.

**Может навредить** на запросах, различающихся только константами: они образуют
один класс, модель учит среднее. Редкое значение за пределами MCV получило
оценку хуже, чем у чистого планировщика — 9.8x против 16.1x.

## Протокол проверки до и после

1. До включения снять `EXPLAIN (ANALYZE)` и запомнить **форму плана**. Время
   мерить отдельными прогонами без инструментации: `EXPLAIN ANALYZE` на больших
   сканах завышал время до 15 раз (hash join — 19.6 с против 300 с).
2. Обучить: `aqo.advanced = on` обязательно, режим `learn`, затем `frozen`.
3. Снять форму плана снова. **Не изменилась — выигрыша не будет.** Этот шаг
   отсекает восемь случаев из девяти за минуту.
4. Изменилась — мерить время чередующимися сериями base/aqo, считать межсерийный
   разброс и сравнивать дельту с ним. У нас разброс доходил до 26 %, и дважды
   пришлось снимать поспешные выводы.
5. `aqo_cardinality_error()` для решения не использовать: функция показывала
   нулевую ошибку там, где времени не убавилось ни на процент.

## Особенности расширения, найденные по ходу

- **Дефолтная конфигурация нерабочая.** При `aqo.advanced = off` все запросы
  складываются в общий класс `fs = 0` с `learn_aqo = false`, `use_aqo = false`, а
  `aqo_cardinality_error()` и `aqo_execution_time()` не возвращают ничего.
  Раздельные классы появляются только при `advanced = on`.
- **Оверхед обучения** около 25 %: `q2` в режиме `learn` шёл 11.7 с против 9.3 с
  без `aqo`, стабильно по всем десяти итерациям.
- **Кривая обучения плоская**: за десять итераций время не менялось — модель либо
  влияет с первых прогонов, либо не влияет вовсе.
- **`aqo.debug_print`** присутствует в `pg_settings`, но отсутствует в
  документации и для 17, и для 18.
- **`default_statistics_target` в сборке Postgres Pro равен 800**, а не 100 как в
  ванильном PostgreSQL. MCV-список в восемь раз длиннее, и это меняет постановку
  любого эксперимента про качество оценок.

## Датасет

Звезда: `fact_sales` (60 млн строк, 6.7 GB с индексами) и справочники
`customers` (2 млн), `products` (200 тыс.), `stores` (1 тыс.), `suppliers` (500).
База — 7 GB, помещается в кеш намеренно.

Все случайные величины детерминированы: вместо `random()` везде хеш от номера
строки, поэтому датасет воспроизводится побайтово даже при параллельной
генерации в шесть процессов. Шесть механизмов ошибок планировщика заложены в
данные так, чтобы силу каждого можно было менять без перегенерации таблицы
фактов — подробности в [`ROADMAP.md`](ROADMAP.md).

## Как повторить

```bash
bash scripts/00-setup.sh                 # стенд, конфиг, база aqotest
bash scripts/01-dataset.sh               # датасет (ROWS, CORR — параметры)
bash scripts/02-baseline.sh              # базовая линия без aqo
bash scripts/03-statistics.sh            # контрольная линия CREATE STATISTICS
bash scripts/04-aqo-learn.sh             # обучение и замер в frozen
bash scripts/05-repeat.sh                # межсерийный разброс
bash scripts/06-cold.sh                  # холодный кеш
bash scripts/07-costmodel.sh             # стоимостная модель против кардинальности
bash scripts/08-final.sh                 # итоговая серия на верной стоимости
```

## Что внутри

- `scripts/` — скрипты стенда в порядке запуска;
- `data/` — сырые результаты всех серий, `data/plans/` — снятые планы;
- `ROADMAP.md` — ход работы со всеми поворотами, включая снятые выводы.
