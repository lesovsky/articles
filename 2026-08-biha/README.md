# BiHA: материалы серии

Данные и скрипты к серии статей про встроенную отказоустойчивость BiHA в
Postgres Pro Enterprise.

**Здесь материалы первой статьи** — «Postgres Pro BiHA на практике: аварийное
тестирование встроенной отказоустойчивости». Данные следующих частей появятся
вместе со своими статьями, чтобы результаты не опережали текст.

## Вопрос первой статьи

Лидер умер — сколько времени приложение не может писать, от чего это зависит и
что можно сделать.

## Короткие ответы

**Собственное время кластера — около двадцати секунд**, и оно почти не зависит
от того, как именно умер лидер: штатная остановка, `kill -9`, перезагрузка узла,
сетевая изоляция, зависание процессов. По фазам обнаружения и повышения способ
отказа вообще неразличим.

**А вот приложение узнаёт об этом когда придётся:**

| Отказ лидера | клиент по умолчанию | `tcp_user_timeout=5000` | + дедлайн запроса |
|---|---:|---:|---:|
| штатная остановка | 20.96 с | — | — |
| `kill -9` | 20.33 с | 21.40 с | — |
| перезагрузка узла | 27.21 с | 21.68 с | — |
| сетевая изоляция | **≥ 110 с, не восстановился** | 21.89 с | — |
| зависание `SIGSTOP` | **≥ 61 с, граница опыта** | **≥ 61 с, граница опыта** | **21.41 с** |

Сетевые таймауты закрывают потерю пакетов, но не заморозку: ядро замороженного
узла продолжает подтверждать пакеты, и таймауту, который считает неподтверждённые
данные, засекать нечего. Заморозку берёт только прикладной дедлайн на запрос.

**`heartbeat_send_period` — главные часы.** Обнаружение отказа в точности равно
`send_period × max_lost`, а выборы с повышением стоят около пяти периодов сверху.
У обоих параметров жёсткий минимум — 500 мс и 3, — поэтому меньше девяти секунд
простоя на этой конфигурации не получить.

Полные таблицы, разбросы и оговорки — в [`RESULTS.md`](RESULTS.md).

## Позиция автора

Материал снят с позиции DBA-пользователя, а не разработчика системы: описывается
только наблюдаемое — процессы в ОС, представления и функции в SQL, метки в логе,
секундомер со стороны клиента. Внутренняя механика остаётся чёрным ящиком с
наблюдаемыми краями.

## Как повторить

```bash
bash scripts/00-access.sh        # разложить ssh-ключ на узлы стенда
bash scripts/01-normalize.sh     # погасить лишнее, выровнять логирование
bash scripts/run-matrix.sh 3     # матрица отказов лидера
bash scripts/run-timeouts.sh 3   # то же с клиентскими таймаутами
bash scripts/run-hbsweep.sh      # развёртка по бюджету обнаружения
bash scripts/tcp-probe.sh sigstop        # состояние сокета при заморозке
python3 scripts/summary.py               # сводная таблица по всем прогонам
python3 scripts/analyze.py <прогон>      # разбор одного прогона по фазам
```

Адреса узлов и роли — в `scripts/hosts.sh`.

## Стенд

| | |
|---|---|
| СУБД | Postgres Pro Enterprise 18.6, расширение `biha` 1.8 |
| ОС | Debian 12, ядро 6.1.0-51 |
| Узлы | 4 VM по 2 vCPU / 1 GB RAM / 20 GB |
| Кластер | 3 узла, четвёртый — нагрузчик, в кластер не входит |

Стенд слабый намеренно — он давался на 72 часа. Для таймингов failover это
неважно: меряется время реакции, а не пропускная способность.

## Что внутри

- `RESULTS.md` — измерения первой статьи с методикой, разбросами и граблями;
- `scripts/` — обвязка стенда в порядке запуска, `scripts/stand/` — то, что живёт на узле-нагрузчике;
- `data/runs/` — по каталогу на прогон: события клиента, подтверждённые записи, состояние кластера, логи узлов;
- `data/inventory/` — инвентарь наблюдаемого и проверки, снятые со стенда.
