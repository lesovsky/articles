# Результаты экспериментов — серия про BiHA

Все замеры сняты 28–29 августа 2026 на одном стенде, одной обвязкой. Каждая
цифра воспроизводима: `scripts/` в порядке запуска, сырые данные в `data/runs/`
(по каталогу на прогон), метод разбора — `scripts/analyze.py` и
`scripts/summary.py`.

**Стенд.** Postgres Pro Enterprise 18.6, расширение `biha` 1.8, Debian 12
(ядро 6.1.0-51), 4 VM по 2 vCPU / 1 GB RAM / 20 GB на одном разделе.

Состав кластера менялся по ходу работы:

Кластер: `…31.145`, `…30.128`, `…31.13`. Нагрузчик: `…30.212`, в кластер не
входит. Роли задаются переменными `PGNODES` / `MEMBERS` / `LOAD` в
`scripts/hosts.sh` — в материалах следующих статей состав кластера меняется.
Стек мониторинга PPEM остановлен и снят с автозапуска: узлы перезагружаются в
экспериментах, сервисы не должны возвращаться.

**Конфигурация кластера, если не оговорено иное:** `heartbeat_send_period = 1000`,
`heartbeat_max_lost = 10`, `nquorum = 2`, `minnodes = 2`, репликация
асинхронная (`sync_standbys_min = -2`), `biha.autorewind = on`.

> `autorewind` по умолчанию **выключен**; включён намеренно — иначе каждый
> прогон с убийством лидера заканчивался бы `NODE_ERROR` и ручной пересборкой
> узла (§5). На тайминги failover не влияет: параметр касается только
> возвращения выбывшего узла.

## 0. Чем меряли

Три прибора, работающие одновременно, с общей шкалой времени (NTP на всех узлах,
расхождение между узлами до 40 мс).

**Клиентский секундомер** (`scripts/stand/writer.py`) — главный прибор. Пишет
`INSERT ... RETURNING` в цикле с узла 4, через libpq со списком всех трёх узлов
и `target_session_attrs=read-write`, порядка 200 вставок в секунду (по прогонам
139–297, медиана 176; разрешение по времени ~5 мс). Фиксирует последнюю успешную запись до отказа,
первую ошибку, первую успешную запись после и все переподключения. Он же даёт
RPO: множество подтверждённых сервером `seq` сверяется с тем, что осталось в
базе после failover.

**Сборщик состояния** (`scripts/stand/collector.py`) — опрашивает `biha.status_v`
на каждом узле отдельно, раз в 250 мс, коротким таймаутом. Нужен, чтобы
сопоставить «что кластер говорит о себе» с «что видит клиент». Недоступность
узла тоже пишется — это данные, а не сбой.

**Инжектор отказов** (`scripts/inject.sh`) — вносит и снимает отказ, печатая
метку времени **часами самого узла**, в одной удалённой команде с действием.

### Методические решения

- **Метка отказа снимается на узле, а не на рабочей машине.** Часы рабочей
  машины разошлись с узлами почти на две секунды, и первые прогоны показывали
  ошибку клиента *раньше* момента отказа. Узлы между собой согласованы.
- **Простой считается по клиенту**, а не по состоянию кластера: от последней
  успешной записи до первой успешной после. Всё остальное — вторая шкала.
- **Отказ всегда одиночный.** Одновременный вывод двух узлов из трёх отнимает у
  лидера кворум, и это уже сценарий следующей статьи.
- **Логирование выровнено на всех узлах** (`log_line_prefix`, UTC, ротация
  выключена) — фазы снимаются по меткам из логов.
- **Между прогонами кластер обязан вернуться в здоровое состояние**, иначе серия
  останавливается.

### Маркеры фаз в логе

| Фаза | Строка |
|---|---|
| детект обрыва | `[BiHA BCP ...] broken connection on socket` |
| фенсинг лидера | `[BiHA PGC] requested Postgres restart for demotion` |
| уход в read-only | `database system is ready to accept read-only connections` |
| смена состояния | `[BiHA NC <level> <id> <STATE>] state switched` |
| promote начат | `[BiHA PGC] Postgres promotion has been triggered` |
| promote завершён | `[BiHA PGC] Postgres is promoted` |

## 1. Матрица отказов лидера

Пять типов отказа, по три повтора. `data/runs/<тип>-leader-r<N>/`.

### 1.1. Кластер во всех сценариях ведёт себя одинаково

| Фаза (медиана) | T от момента отказа |
|---|---:|
| узел объявлен потерянным (`online=false`) | 8.2–10.8 с |
| начались выборы (`CANDIDATE`) | 12.8–15.1 с |
| `promote` запущен | 19.5–21.1 с |

Разброс между типами отказа меньше разброса между повторами одного типа.
**Со стороны кластера безразлично, как именно исчез лидер.**

### 1.2. Со стороны клиента разница в пять раз

Медиана простоя записи, три повтора на ячейку:

| Отказ лидера | клиент по умолчанию | `tcp_user_timeout=5000` | + дедлайн запроса 5 с |
|---|---:|---:|---:|
| штатная остановка (`systemctl stop`) | 20.96 | — | — |
| `kill -9` всем процессам postgres | 20.33 | 21.40 | — |
| sysrq-перезагрузка узла | 27.21 | 21.68 | — |
| сетевая изоляция (DROP 5432/5433) | **110.2 ⚠** | 21.89 | — |
| заморозка `SIGSTOP` | **60.9 ⚠** | **60.9 ⚠** | **21.41** |

⚠ — **граница опыта, а не измеренная величина**: клиент восстановился только
после того, как отказ снял экспериментатор, либо не восстановился вовсе. При
изоляции клиент провисел 110 секунд и получил первую ошибку уже после конца
прогона. Настоящее значение ограничено таймаутами TCP.

Разброс между повторами в трёх измеренных строках: 0.4–6.3 %. В двух строках
с пометкой ⚠ он тоже мал (0.2 %), но воспроизводится там длительность опыта, а
не длительность простоя.

### 1.3. Почему уровни защиты разные

**Обрыв соединения не ускоряет детект.** Фолловеры видят `broken connection` на
T+0.02, но узел объявляется потерянным всё равно через ~9.4 с, по полному
бюджету heartbeat. Разложение `kill9-leader-r1`:

| T | Событие |
|---:|---|
| +0.02 | фолловеры видят `broken connection` |
| +0.03 | клиент получает первую ошибку |
| +9.38 | узел объявлен потерянным |
| +13.49 | `CANDIDATE` — начались выборы |
| +20.26 | `promote` запущен |
| +20.33 | первая успешная запись клиента |

**`tcp_user_timeout` не берёт заморозку.** При `SIGSTOP` ядро узла живо и
продолжает подтверждать пакеты, складывая их в буфер сокета. Неподтверждённых
данных нет, и таймаут, который считает именно их, не срабатывает никогда. Это
видно прямо в данных: за всю заморозку клиент получил одну ошибку, и только
после разморозки. Лечится прикладным дедлайном — уровнем выше сетевого.

### 1.4. Асимметрия самопонижения

| Кто теряет | Что делает | Время |
|---|---|---:|
| лидер теряет кворум, соединения рвутся явно | фенсит себя | ~1.2 с |
| лидер теряет кворум, пакеты теряются молча | фенсит себя | ~21 с, разбор в следующей статье |
| фолловеры теряют лидера | выборы | ~20 с |

Понизить себя лидер может немедленно и в одиночку; выбрать нового — только
договорившись, и договор начинается после признания старого потерянным.

Фенсинг делается **через immediate restart**: `requested Postgres restart for
demotion` → `all server processes terminated; reinitializing` → подъём в standby.
Все клиентские соединения рвутся, при этом `pg_postmaster_start_time()` не
меняется — снаружи сервер выглядит непрерывно работающим.

## 2. Развёртка по бюджету детекта

`kill -9` по лидеру, клиент с `tcp_user_timeout`, два повтора на точку.
`data/runs/hb-<период>-<потерь>-r<N>/`.

| Бюджет | Параметры | Детект | Простой записи | Остаток |
|---:|---|---:|---:|---:|
| 20.0 с | 2000 × 10 | 19.89 | 35.16 | 15.2 |
| 10.0 с | 1000 × 10 (дефолт) | 9.88 | 20.94 | 10.9 |
| 5.0 с | 1000 × 5 | 5.11 | 16.17 | 11.2 |
| 2.5 с | 500 × 5 | 2.46 | 10.85 | 8.4 |
| 1.5 с | 500 × 3 | 1.35 | 9.12 | 7.6 |

**Детект совпадает с бюджетом** `send_period × max_lost` в пределах точности
замера. Расхождения — десятые доли секунды (1.5 -> 1.35, 5.0 -> 5.11), того же
порядка, что разрешение прибора: `collector.py` опрашивает `biha.status_v` раз в
250 мс. Два повтора одной точки расходятся между собой сильнее, чем от номинала
(5.38 и 4.84 при бюджете 5 с). Формулировка «совпадение до сотых» была неверной.

**Остаток зависит от периода, а не от числа потерь:** 500 мс → ~8 с, 1000 мс →
~11 с, 2000 мс → ~15 с. Рабочая модель:

> простой ≈ `send_period` × `max_lost` + 5 × `send_period` + 5 с

Отсюда: **уменьшение периода помогает дважды, уменьшение `max_lost` — один раз.**

**У периода жёсткий пол.** `biha.set_heartbeat_send_period(300)` отвергается:
`heartbeat_send_period must be at least 500 ms`. Минимально достижимый простой на
этой конфигурации — около 9 секунд.

Ложных срабатываний не наблюдалось ни на одной точке, включая 500 × 3. Оговорка
обязательна: стенд в одной локальной сети с задержкой много меньше миллисекунды.

## 3. Прямое наблюдение за TCP-сокетом клиента

Проверка утверждения, на котором держится вывод про бессилие сетевых таймаутов.
`ss -ti` со стороны клиента (`scripts/tcp-probe.sh`, вывод в
`data/inventory/tcp-socket-observation.txt`).

**Заморозка процессов сервера (`SIGSTOP`), соединение в состоянии `ESTAB`:**

```text
ESTAB ... cubic rto:212 ... bytes_acked:49162
```

`rto` держится на 212 мс и не растёт; полей `unacked` и `retrans` нет вовсе;
`bytes_acked` замирает. Неподтверждённых данных нет: запрос доставлен и
подтверждён ядром замороженного узла, клиент ждёт ответа приложения.
`tcp_user_timeout` отсчитывает время по неподтверждённым данным — засекать
нечего, и он не срабатывает.

**Контраст берётся не из `ss`, а из поведения:** при сетевой изоляции тот же
таймаут срабатывает на 5.67 с (`netcut-tut-r1`), то есть там неподтверждённые
данные есть.

**Методическая ловушка, на которую я наступил.** Первая версия замера запускала
нагрузчик с `tcp_user_timeout=5000` и отбрасывала колонку состояния сокета.
Полученные для изоляции `unacked:1`, `retrans:1/1`, `rto` 1000↔2000 выглядели как
повторная передача данных, а при повторном замере с сохранением состояния
оказались **`SYN-SENT`**: исходное соединение умирало по таймауту на пятой
секунде, и дальше наблюдались уже попытки подключения с повторной передачей SYN
(начальный RTO 1000 мс, удвоение до 2000, локальный порт меняется от замера к
замеру). Числа складывались в правдоподобную, но неверную картину. Вывод: при
наблюдении за сокетом состояние надо снимать всегда, иначе
`unacked` / `retrans` / `rto` интерпретируются наугад.

**Оговорка про область действия `tcp_user_timeout`.** По `man 7 tcp` он покрывает
две ситуации: переданные данные остаются неподтверждёнными **либо**
буферизованные данные остаются непереданными из-за нулевого окна. Замороженный
сервер со временем даёт второй случай: ядро складывает пакеты в буфер, приложение
их не читает, окно схлопывается. В наших замерах до этого не дошло — нагрузчик
пишет короткие вставки и за 60 с буфер не заполнил. Поэтому формулировка «класс
"сервер жив, но не отвечает" не закрывается сетевым таймаутом в принципе» неверна:
закрывается, но за время, зависящее от размера буфера и объёма записи, а не от
настройки.

## 4. Нижние границы обоих параметров heartbeat

Дословно со стенда (`data/inventory/fact-check-verifications.txt`):

```text
ERROR:  [BiHA] biha.set_heartbeat_send_period() failed:
        heartbeat_send_period must be at least 500 ms, but passed value is 300 ms
ERROR:  [BiHA] biha.set_heartbeat_max_lost() failed:
        heartbeat_max_lost must be at least 3, but passed value is 2
```

Минимум есть у обоих параметров. Значит точка `500 × 3` в развёртке (§2) — не
произвольная нижняя точка, а **предельно агрессивная настройка из возможных**, и
полученные на ней 9.12 с — доказанная нижняя граница простоя записи, а не просто
лучший результат серии.

## 5. Без `autorewind` кластер не самовосстанавливается

После первого же `kill -9` по лидеру убитый узел поднялся в `NODE_ERROR`:
`Node was diverged and not ready: rewind was not performed or had failed`.
Расхождение — 200 байт WAL (`source LSN 0/2A8AA10`, `my LSN 0/2A8AAD8`). В логе:
`trying to trim WAL by removing WAL divergence to prevent rewind` → `Need to
rewind from node-1` → `manual rewind required`.

`biha.reset_node_error()` выводит узел из состояния, но при следующем старте он
возвращается туда же: причина не во флаге, а в неустранённом расхождении.
Включение `biha.autorewind = on` **задним числом не чинит** — параметр работает,
только если был включён до отказа.

Восстановление потребовало вывода узла из кластера и полной пересборки:
`biha.remove_node(3)` (принимается только когда лидер видит узел `online=false`)
→ очистка `PGDATA` → `bihactl add` с `pg_basebackup`. Процедура —
`scripts/reset-node.sh`.

## 6. Методические грабли обвязки

Все четыре найдены на себе и исправлены; каждая успела испортить прогоны.

1. **`ssh` не отпускает фоновый процесс.** `nohup`, `setsid`, `-n` и полное
   перенаправление не освобождают канал: скрипт блокировался на всю длительность
   прогона, и отказ приходился уже после его конца. Нагрузчик и сборщик держатся
   открытыми ssh-сессиями в фоне **на рабочей машине**.
2. **Часы рабочей машины разошлись с узлами на две секунды** — первые прогоны
   показывали ошибку клиента раньше момента отказа. Метка снимается на узле.
3. **Логи копировались по имени `postgresql-<сегодня>.log`**, а ротация выключена
   и файл назван по дате старта сервера. У всех прогонов после полуночи UTC логи
   были пустыми; дозабраны `scripts/refetch-logs.sh`. Плюс глоб в пути
   разворачивался непривилегированным shell'ом, который не может читать каталог
   логов, — нужен `sudo sh -c`.
4. **Сводка молча выбрасывала прогоны, где клиент не восстановился** — то есть
   ровно худшие случаи. Теперь они помечаются явно.

Отдельно — ловушка не в обвязке, а в клиентском коде, и она попала в результаты
как измеренный эффект. Первая версия нагрузчика по истечении прикладного дедлайна
пыталась закрыть зависшее соединение. `close()` блокируется, потому что соединение
держит зависший поток, — клиент встал сам, дав одну попытку переподключения и
**61 секунду простоя вместо 21** при формально правильном таймауте. Брошенное по
дедлайну соединение закрывать нельзя, ссылку надо терять.
