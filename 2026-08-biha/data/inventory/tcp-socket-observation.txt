# Состояние TCP-сокета клиента при отказе сервера
# Снято ss -ti со стороны клиента. Скрипт: scripts/tcp-probe.sh

## Заморозка процессов сервера (SIGSTOP) — состояние ESTAB
до отказа:  ESTAB rto:208 rtt:5.882/0.34 bytes_sent:29276 bytes_acked:29180
T+3..18s:   ESTAB rto:212 (не меняется), bytes_acked:49162 (заморожен),
            полей unacked и retrans НЕТ

Неподтверждённых данных нет: запрос доставлен и подтверждён ядром замороженного
узла, клиент ждёт ответа приложения. tcp_user_timeout отсчитывает время по
неподтверждённым данным — засекать нечего.

## Потеря пакетов (nft DROP) — ЧТО ЗДЕСЬ ПОШЛО НЕ ТАК

Первый замер (нагрузчик с tcp_user_timeout=5000, состояние сокета отброшено):
T+3s:  rto:2000 unacked:1 retrans:1/1
T+6s:  rto:1000 unacked:1
...
Выглядело как повторная передача ДАННЫХ. Повторный замер с сохранением состояния
показал, что это НЕ ТАК:

T+9s:   SYN-SENT ... rto:2000 backoff:1 cwnd:1 ssthresh:7 segs_out:2  порт 60934
T+12s:  SYN-SENT ... rto:1000 cwnd:10 segs_out:1                      порт 60940
T+15s:  SYN-SENT ... rto:2000 backoff:1 cwnd:1 ssthresh:7 segs_out:2  порт 60946
T+18s:  SYN-SENT ... rto:1000 cwnd:10 segs_out:1                      порт 53834

Локальный порт меняется от замера к замеру — это повторные передачи SYN при
попытках подключения, а не судьба отправленного запроса. Исходное соединение
умирало по tcp_user_timeout на пятой секунде.

## Вывод

Наблюдением подтверждено только поведение при заморозке — и этого достаточно:
именно на нём держится вывод про бессилие сетевых таймаутов.

Контраст берётся из поведения, а не из ss: при сетевой изоляции tcp_user_timeout
срабатывает на 5.67 с (netcut-tut-r1), значит неподтверждённые данные там есть.

Методический урок: при наблюдении за сокетом состояние (ESTAB / SYN-SENT) надо
снимать всегда, иначе unacked/retrans/rto интерпретируются наугад.
