## 0. Методическая находка: `io_method = sync` — это НЕ «до-AIO поведение»

Ключевой факт, меняющий интерпретацию всей матрицы. При `sync` read stream всё равно
строит очередь глубиной `effective_io_concurrency`, используя старый
`posix_fadvise(WILLNEED)`. Подтверждено strace (bitmap heap scan, ~58 800 блоков):

| Конфигурация | Системные вызовы бэкенда |
|---|---|
| `sync`, `eic=16` | 58 655 × `fadvise64` + 58 739 × `pread64` |
| `sync`, `eic=0` | 59 259 × `pread64`, ни одного `fadvise64` |
| `worker`, `eic=16` | 5 153 × `epoll_wait` + 5 152 × `read` + **196 × `pread64`** |
| `io_uring`, `eic=16` | 58 648 × `io_uring_enter` + 81 × `pread64` |

Следствия:

1. Настоящий синхронный baseline (QD1) — это `sync` + **`eic = 0`**, а не просто `sync`.
2. При `worker` бэкенд практически не читает сам: 196 `pread64` из ~58 800 блоков.
   99.7% чтений выполнили io-воркеры, бэкенд только принимал уведомления.
3. Ось «sync vs AIO» из §5 роадмапа измеряет не «синхронное против асинхронного»,
   а «fadvise-префетч против AIO».

## 1. Bitmap heap scan — выигрыш есть, но не от AIO

Запрос: `SELECT sum(id) FROM bench WHERE sel_key >= N AND sel_key < N+1000`.
Селективность 0.1% строк (60 142 строки) = **1.39% страниц** (59 745 из 4 285 715),
≈ 460 MB разреженного чтения. Одна сессия, холодный старт, разные диапазоны.

`sum(id)`, а не `count(*)`: `id` нет в индексе, иначе планировщик уходит в Index Only
Scan по индексу на 401 MB и heap не читается вовсе (`Heap Fetches: 0`, 28 мс).

| Конфигурация | Время | waits/count | Комментарий |
|---|---|---|---|
| `sync`, `eic=0` | 12 484 / 12 667 мс | 100% | истинный QD1 |
| `worker`, `eic=16`, пул 2–8 | 1930 / 1955 мс | 40% | **дефолт PG 19** |
| `worker`, `eic=16`, пул 8 | 1975 мс | 41% | пул не помогает |
| `worker`, `eic=64`, пул 8 | 1758 мс | 38% | |
| `sync`, `eic=16` | 1069 мс | 100% | fadvise |
| `sync`, `eic=64` | 1074 мс | 100% | полка |
| `sync`, `eic=128` | 975 мс | 100% | полка |
| `io_uring`, `eic=16` | 1207 мс | 27% | |
| **`io_uring`, `eic=64`** | **804 мс** | **13%** | лучший результат |

Выводы:

- Дефолтный `worker` **медленнее старого fadvise-пути** (1930 против 1069 мс) и не
  ускоряется от увеличения пула — упирается в стоимость IPC, а не в число воркеров.
- `io_uring` масштабируется по глубине очереди (1207 → 804 при `eic` 16 → 64),
  `sync` выходит на полку около `eic=16` (1069 → 975 при 16 → 128).
- Для DBA, апгрейднувшегося с 17 на дефолтах, bitmap scan всё равно ускорится
  ≈ ×6.5 (12.5 с → 1.93 с), но **за счёт смены дефолта `effective_io_concurrency`
  с 1 на 16, а не за счёт AIO**.
- Метрика `waits` обманчива: у `sync` ждут 100% операций, и он при этом быстрее
  `worker` с его 40%.

## 2. Seq scan — здесь AIO даёт реальное ускорение

`SELECT sum(id) FROM bench` — 33 GB, 267 862 операции чтения по 128 kB
(`size=16.00` блоков = `io_combine_limit`).

| Конфигурация | Время | MB/s | waits/count |
|---|---|---|---|
| `sync`, `eic=0` | 61 239 мс | 546 | 267862 / 267862 |
| `sync`, `eic=16` | 61 426 мс | 545 | 267862 / 267862 |
| `worker`, `eic=16` | **31 532 мс** | **1060** | 244580 / 267862 |
| `io_uring`, `eic=16` | **31 572 мс** | 1058 | 229568 / 267862 |

- AIO даёт **×1.95**, `worker` и `io_uring` неразличимы.
- `effective_io_concurrency` на seq scan при `sync` **не влияет вообще** (61.2 против
  61.4 с) — fadvise-префетч здесь не применяется, работает только readahead ядра
  (`read_ahead_kb = 128`).
- Тезис 8 роадмапа подтверждён: seq scan выигрывает от AIO, и исходное предположение
  «на seq scan разницы почти не будет» опровергнуто.

**Сверка с потолком железа.** fio-baseline из сессии 1 (808 MB/s) оказался занижен —
он снимался на файле 8 GB. Перемер на файле 12 GB: seqread 128k QD16 = **1058 MB/s**,
QD32 = 1013 MB/s, 8 потоков по QD2 = 976 MB/s.

То есть PostgreSQL с AIO даёт 1060 MB/s — **ровно физический потолок диска**,
а без AIO 546 MB/s — ровно половину. В посте использовать 1058, а не 808.

## 3. VACUUM — тот же выигрыш, тоже чисто от AIO

`VACUUM (DISABLE_PAGE_SKIPPING) bench` — принудительное чтение всех 33 GB
(без флага таблица all-visible после FREEZE и вакуум не прочитал бы ничего).

| Конфигурация | Время | read_time |
|---|---|---|
| `sync`, `mio=0` | 59 246 мс | 53 368 мс |
| `sync`, `mio=16` | 60 194 мс | 53 933 мс |
| `worker`, `mio=16` | **32 069 мс** | 24 110 мс |
| `io_uring`, `mio=16` | **32 168 мс** | 25 354 мс |
| `io_uring`, `mio=64` | 33 518 мс | 26 711 мс |

- AIO даёт **×1.85**, `maintenance_io_concurrency` не влияет (59.2 против 60.2 с).
- Рост `mio` до 64 слегка вредит (33.5 против 32.2 с).
- В `sync` 90% времени вакуума — ожидание чтения (53.4 из 59.2 с), при AIO — 75%.

## 4. Пул io-воркеров: фиксированный против адаптивного (главный график)

Bitmap heap scan, каждая сессия читает свой диапазон `sel_key` шириной 1000
(≈460 MB), 3 повтора, берётся медиана по самой медленной сессии итерации.
`effective_io_concurrency = 16` (дефолт) во всех ячейках.

| Сессий | fixed3 (эмуляция 18) | adaptive 2–8 (дефолт 19) | fixed8 | `io_uring` | `sync` (fadvise) |
|---|---|---|---|---|---|
| 1 | 4236 | 2102 | 1974 | 1351 | **1348** |
| 2 | 8250 | 3928 | 3804 | 1814 | **1748** |
| 4 | 16233 | 7452 | 7360 | 3396 | **3337** |
| 8 | 17169 | 9871 | 10480 | 6448 | **6060** |
| 16 | 19196 | 13582 | 13967 | 13099 | **11662** |

Выводы:

- **Адаптивный пул статистически неотличим от фиксированного пула из 8** на всех
  уровнях (2102/1974, 3928/3804, 7452/7360, 9871/10480, 13582/13967). Адаптивность
  не даёт выигрыша в скорости — она избавляет от необходимости угадывать число.
  Это и есть практический смысл фичи 19: не «стало быстрее», а «не надо настраивать».
- **Фиксированный пул из 3** (дефолт 18) отстаёт вдвое на низкой конкурентности
  (4236 против 2102) и остаётся худшим везде.
- **`worker` проигрывает `sync` и `io_uring` на всех уровнях конкурентности.**
  Наибольший разрыв при 2 сессиях: 3928 против 1748, то есть ×2.2.
- У `sync`/`io_uring` переход 1 → 2 сессии почти бесплатен (1348 → 1748 мс при
  удвоении объёма работы) — диск далёк от насыщения. У `worker` рост почти линейный
  (2102 → 3928): пул воркеров упирается в себя уже на одной сессии.
- При 16 сессиях разрыв между методами сокращается — все упираются в диск
  (631 MB/s у `sync` против 542 MB/s у adaptive).

## 5. Развёртка `effective_io_concurrency` — AIO без очереди не работает

Bitmap heap scan, минимум из 2 итераций, мс:

| `eic` | `sync` | `worker` | `io_uring` |
|---|---|---|---|
| 0 | 12651 | 12609 | 12732 |
| 1 | 12632 | 13853 | 12684 |
| 4 | 3165 | 4560 | 3447 |
| 16 (дефолт 18/19) | 1170 | 2005 | 1225 |
| 64 | 1045 | 1974 | **856** |
| 128 | 1016 | 1962 | **863** |

- **При `eic` = 0 и 1 все три метода неразличимы** (~12.6 с). Без глубины очереди
  AIO не даёт ничего.
- Проверено и на seq scan: при `eic = 0` `worker` даёт 61 253 мс, `io_uring` —
  61 099 мс, `sync` — 61 239 мс. Полностью идентично.
  **`effective_io_concurrency = 0` — это выключатель AIO на любом сценарии.**
- `worker` выходит на полку (~1960 мс) уже при `eic=16` и дальше не растёт.
- `sync` выходит на полку ~1020 мс при `eic` 64–128.
- `io_uring` — единственный, кто продолжает выигрывать от глубины очереди.
- Курьёз: `worker` при `eic=1` (13853 мс) медленнее, чем при `eic=0` (12609 мс) —
  накладные расходы AIO без какого-либо выигрыша.

## 6. Развёртка `io_combine_limit` — на seq scan решает объединение блоков

Seq scan 33 GB, минимум из 2 итераций, мс. `io_max_combine_limit = 32` во всех
ячейках (иначе значения выше 16 недоступны; параметр меняется только при старте):

| Блоков в операции | `sync` | `worker` |
|---|---|---|
| 1 (8 kB) | 61 500 | **62 540** |
| 4 (32 kB) | 61 022 | 45 307 |
| 16 (128 kB, дефолт) | 59 132 | 32 314 |
| 32 (256 kB) | 46 266 | 31 800 |

- **При `io_combine_limit = 1` AIO не даёт ничего** (62 540 против 61 500 у `sync`).
  Весь выигрыш AIO на seq scan держится на объединении соседних блоков в крупные
  операции, а не на асинхронности самой по себе.
- Подъём до 256 kB ускоряет и синхронный путь (59.1 → 46.3 с), но требует поднять
  ещё и `io_max_combine_limit` и рестартовать сервер.

```
 ->  Bitmap Heap Scan on bench (actual time=23.371..1929.482 rows=59826.00 loops=1)
       Recheck Cond: ((sel_key >= 5000) AND (sel_key < 6000))
       Heap Blocks: exact=59456

       I/O: count=58623 waits=24259 size=1.01 in-progress=16.00
```

Строка `I/O:` — это и есть новое в 19. `count` — сколько операций, `waits` — сколько
из них пришлось дождаться, `size` — средний размер в блоках, `in-progress` — глубина
очереди на момент завершения.

| `io_uring` | 68 |
| `worker` | 335 |

При `sync` представление практически пусто — операции не «висят», они выполняются
синхронно. Состояния: `SUBMITTED`, `COMPLETED_SHARED`; операция `readv`, target `smgr`.

### Картина ожиданий меняется вместе с `io_method`

Свой сэмплер, 100 опросов/с, доли по сэмплам без фоновых процессов и без `Activity`.
Bitmap heap scan:

| Конфигурация | Кто ждёт | На чём | Доля |
|---|---|---|---|
| `sync`, `eic=0` | client backend | `IO / DataFileRead` | 97.5% |
| `sync`, `eic=16` | client backend | `IO / DataFileRead` | 59.3% |
| | client backend | **`IO / DataFilePrefetch`** | 14.2% |
| `worker` | **io worker** | `IO / DataFileRead` | 85.1% |
| | client backend | `IO / AioIoCompletion` | 9.8% |
| | client backend | `IO / DataFileRead` | **0.6%** |
| `io_uring` | client backend | `IO / AioIoUringExecution` | 73.0% |
| | client backend | `IO / AioIoUringSubmit` | 10.3% |

Seq scan даёт ту же структуру: `worker` — io worker на `DataFileRead` 87.2% и бэкенд
на `AioIoCompletion` 8.2%; `io_uring` — бэкенд на `AioIoUringExecution` 62.5%;
`sync` — бэкенд на `DataFileRead` 84.2%.

Три метода дают три качественно разные картины в `pg_stat_activity` — ровно тот
сюжет из §2.5 роадмапа. Отдельно ценно, что `DataFilePrefetch` виден напрямую:
это и есть fadvise, который отличает `sync` от истинного QD1.

**Практическое следствие для DBA:** привычный поиск `wait_event = 'DataFileRead'`
у клиентских бэкендов после перехода на `worker` перестаёт находить нагрузку —
чтение уехало в процессы `io worker`, а бэкенд ждёт на `AioIoCompletion`.
