## 0. Методическая находка: `io_method = sync` — это НЕ «до-AIO поведение»

Ключевой факт, меняющий интерпретацию всей матрицы. При `sync` read stream всё равно
строит очередь глубиной `effective_io_concurrency`, используя старый
`posix_fadvise(WILLNEED)`. Подтверждено strace (bitmap heap scan, ~58 800 блоков):

| Конфигурация | Системные вызовы бэкенда |
|---|---|
| `sync`, `eic=16` | 58 655 × `fadvise64` + 58 739 × `pread64` |
| `sync`, `eic=0` | 59 259 × `pread64`, ни одного `fadvise64` |
| `worker`, `eic=16` | 5 153 × `epoll_wait` + 5 152 × `read` + **196 × `pread64`** |
| `io_uring`, `eic=16` | 58 648 × `io_uring_enter` + 81 × `pread64` |

> **Сессия 3: пересняно, артефакт сохранён.** В сессии 2 эти числа были
> опубликованы без сырого вывода, то есть не проверяемы. Пересъёмка —
> `scripts/12-strace.sh`, вывод — `data/observ/strace/*.txt`:
> `sync eic=16` → 58 620 `fadvise64` + 58 705 `pread64`;
> `sync eic=0` → 58 705 `pread64`, ни одного `fadvise64`;
> `worker eic=16` → 3 564 `epoll_wait` + 182 `pread64`;
> `io_uring eic=16` → 58 615 `io_uring_enter` + 82 `pread64`.
> Отличия от сессии 2 — в пределах прогона, выводы те же.

Следствия:

1. Настоящий синхронный baseline (QD1) — это `sync` + **`eic = 0`**, а не просто `sync`.
2. При `worker` бэкенд практически не читает сам: 196 `pread64` из ~58 800 блоков.
   99.7% чтений выполнили io-воркеры, бэкенд только принимал уведомления.
3. Ось «sync vs AIO» из §5 роадмапа измеряет не «синхронное против асинхронного»,
   а «fadvise-префетч против AIO».

## 1. Bitmap heap scan — выигрыш есть, но не от AIO

Запрос: `SELECT sum(id) FROM bench WHERE sel_key >= N AND sel_key < N+1000`.
Селективность 0.1% строк (60 142 строки) = **1.39% страниц** (59 745 из 4 285 715),
≈ 460 MB разреженного чтения. Одна сессия, холодный старт, разные диапазоны.

`sum(id)`, а не `count(*)`: `id` нет в индексе, иначе планировщик уходит в Index Only
Scan по индексу на 401 MB и heap не читается вовсе (`Heap Fetches: 0`, 28 мс).

| Конфигурация | Время | waits/count | Комментарий |
|---|---|---|---|
| `sync`, `eic=0` | 12 484 / 12 667 мс | 100% | истинный QD1 |
| `worker`, `eic=16`, пул 2–8 | 1930 / 1955 мс | 40% | **дефолт PG 19** |
| `worker`, `eic=16`, пул 8 | 1975 мс | 41% | пул не помогает |
| `worker`, `eic=64`, пул 8 | 1758 мс | 38% | |
| `sync`, `eic=16` | 1069 мс | 100% | fadvise |
| `sync`, `eic=64` | 1074 мс | 100% | полка |
| `sync`, `eic=128` | 975 мс | 100% | полка |
| `io_uring`, `eic=16` | 1207 мс | 27% | |
| **`io_uring`, `eic=64`** | **804 мс** | **13%** | лучший результат |

Выводы:

- Дефолтный `worker` **медленнее старого fadvise-пути** (1930 против 1069 мс) и не
  ускоряется от увеличения пула — упирается в стоимость IPC, а не в число воркеров.
- `io_uring` масштабируется по глубине очереди (1207 → 804 при `eic` 16 → 64),
  `sync` выходит на полку около `eic=16` (1069 → 975 при 16 → 128).
- Для DBA, апгрейднувшегося с 17 на дефолтах, bitmap scan всё равно ускорится
  ≈ ×6.5 (12.5 с → 1.93 с), но **за счёт смены дефолта `effective_io_concurrency`
  с 1 на 16, а не за счёт AIO**.
- Метрика `waits` обманчива: у `sync` ждут 100% операций, и он при этом быстрее
  `worker` с его 40%.

## 2. Seq scan — здесь AIO даёт реальное ускорение

`SELECT sum(id) FROM bench` — 33 GB, 267 862 операции чтения по 128 kB
(`size=16.00` блоков = `io_combine_limit`).

| Конфигурация | Время | MiB/s | waits/count |
|---|---|---|---|
| `sync`, `eic=0` | 61 239 мс | 546 | 267862 / 267862 |
| `sync`, `eic=16` | 61 426 мс | 545 | 267862 / 267862 |
| `worker`, `eic=16` | **31 532 мс** | **1060** | 244580 / 267862 |
| `io_uring`, `eic=16` | **31 572 мс** | 1058 | 229568 / 267862 |

- AIO даёт **×1.95**, `worker` и `io_uring` неразличимы.
- `effective_io_concurrency` на seq scan при `sync` **не влияет вообще** (61.2 против
  61.4 с) — fadvise-префетч здесь не применяется, работает только readahead ядра
  (`read_ahead_kb = 128`).
- Тезис 8 роадмапа подтверждён: seq scan выигрывает от AIO, и исходное предположение
  «на seq scan разницы почти не будет» опровергнуто.

**Сверка с потолком железа.** fio-baseline из сессии 1 (808 MiB/s) оказался занижен —
он снимался на файле 8 GB. Перемер на файле 12 GB: seqread 128k QD16 = **1058 MiB/s**,
QD32 = 1013 MiB/s, 8 потоков по QD2 = 976 MiB/s.

То есть PostgreSQL с AIO даёт 1060 MiB/s — **ровно физический потолок диска**,
а без AIO 546 MiB/s — ровно половину. В посте использовать 1058, а не 808.

## 4. Пул io-воркеров: фиксированный против адаптивного (главный график)

Bitmap heap scan, каждая сессия читает свой диапазон `sel_key` шириной 1000
(≈460 MB), 3 повтора. В каждой итерации берётся самая медленная сессия (это
время всей пачки), затем медиана по трём итерациям.
`effective_io_concurrency = 16` (дефолт) во всех ячейках.

> **Исправлено в сессии 3.** В первой редакции этой таблицы стоял *максимум*
> по итерациям, а подписана она была как медиана — во всех 25 ячейках.
> Пересчитано по `data/results.csv` (`exp = 2`). Выводы не изменились,
> изменились числа на 1–6%.

| Сессий | fixed3 (эмуляция 18) | adaptive 2–8 (дефолт 19) | fixed8 | `io_uring` | `sync` (fadvise) |
|---|---|---|---|---|---|
| 1 | 4201 | 2025 | 1942 | 1342 | **1282** |
| 2 | 8233 | 3857 | 3645 | 1803 | **1741** |
| 4 | 15963 | 7301 | 7227 | 3379 | **3320** |
| 8 | 17079 | 9574 | 9881 | 6277 | **5920** |
| 16 | 19161 | 13359 | 13885 | 12723 | **11250** |

Выводы:

- **Адаптивный пул статистически неотличим от фиксированного пула из 8** на всех
  уровнях (2025/1942, 3857/3645, 7301/7227, 9574/9881, 13359/13885). Адаптивность
  не даёт выигрыша в скорости — она избавляет от необходимости угадывать число.
  Это и есть практический смысл фичи 19: не «стало быстрее», а «не надо настраивать».
- **Фиксированный пул из 3** (дефолт 18) отстаёт вдвое на низкой конкурентности
  (4201 против 2025) и остаётся худшим везде.
- **`worker` проигрывает `sync` и `io_uring` на всех уровнях конкурентности.**
  Наибольший разрыв при 2 сессиях: 3857 против 1741, то есть ×2.2.
- У `sync`/`io_uring` переход 1 → 2 сессии почти бесплатен (1282 → 1741 мс при
  удвоении объёма работы) — диск далёк от насыщения. У `worker` рост почти линейный
  (2025 → 3857): пул воркеров упирается в себя уже на одной сессии.
- При 16 сессиях разрыв между методами сокращается — все упираются в диск
  (654 MiB/s у `sync` против 551 MiB/s у adaptive; 16 × 460 MB прочитанного
  делить на время).

## 5. Развёртка `effective_io_concurrency` — AIO без очереди не работает

Bitmap heap scan, минимум из 2 итераций, мс:

| `eic` | `sync` | `worker` | `io_uring` |
|---|---|---|---|
| 0 | 12651 | 12609 | 12732 |
| 1 | 12632 | 13853 | 12684 |
| 4 | 3165 | 4560 | 3447 |
| 16 (дефолт 18/19) | 1170 | 2005 | 1225 |
| 64 | 1045 | 1974 | **856** |
| 128 | 1016 | 1962 | **863** |

- **При `eic` = 0 и 1 все три метода неразличимы** (~12.6 с). Без глубины очереди
  AIO не даёт ничего.
- Проверено и на seq scan: при `eic = 0` `worker` даёт 61 253 мс, `io_uring` —
  61 099 мс, `sync` — 61 239 мс. Полностью идентично.
  **`effective_io_concurrency = 0` — это выключатель AIO на любом сценарии.**
- `worker` выходит на полку (~1960 мс) уже при `eic=16` и дальше не растёт.
- `sync` выходит на полку ~1020 мс при `eic` 64–128.
- `io_uring` — единственный, кто продолжает выигрывать от глубины очереди.
- Курьёз: `worker` при `eic=1` (13853 мс) медленнее, чем при `eic=0` (12609 мс) —
  накладные расходы AIO без какого-либо выигрыша.

## 6. Развёртка `io_combine_limit` — на seq scan решает объединение блоков

Seq scan 33 GB, минимум из 2 итераций, мс. `io_max_combine_limit = 32` во всех
ячейках (иначе значения выше 16 недоступны; параметр меняется только при старте):

| Блоков в операции | `sync` | `worker` |
|---|---|---|
| 1 (8 kB) | 61 500 | **62 540** |
| 4 (32 kB) | 61 022 | 45 307 |
| 16 (128 kB, дефолт) | 59 132 | 32 314 |
| 32 (256 kB) | 46 266 | 31 800 |

- **При `io_combine_limit = 1` AIO не даёт ничего** (62 540 против 61 500 у `sync`).
  Весь выигрыш AIO на seq scan держится на объединении соседних блоков в крупные
  операции, а не на асинхронности самой по себе.
- Подъём до 256 kB ускоряет и синхронный путь (59.1 → 46.3 с), но требует поднять
  ещё и `io_max_combine_limit` и рестартовать сервер.

Выводы:

1. **На bitmap выбор базы не важен:** `eic=1` и `eic=0` неразличимы (12 705 против
   12 708) — очередь глубиной в единицу это и есть отсутствие очереди. ×6.3 при
   любой базе. Прежнее значение канвы подтверждено.
2. **На seq scan и VACUUM выбор базы меняет цифру,** потому что на 19-й неглубокая
   очередь стоит дороже, чем её отсутствие: seq scan 66.8 с при `eic=1` против
   58.8 с при `eic=0`. **В статье берётся меньшая оценка** (×1.66 и ×1.63):
   в 17-й `effective_io_concurrency` дословно «only affects bitmap heap scans»,
   то есть до seq scan не дотягивался вовсе, а про `maintenance_io_concurrency`
   и heap-скан вакуума документация 17-й не утверждает ничего определённого.
   Приписывать 17-й накладные расходы, которых у неё могло не быть, — значит
   завысить выигрыш апгрейда.
3. **Настройка сверх дефолта 19 работает только на bitmap** (×2.37). На seq scan
   и VACUUM прирост 3% при внутриячеечном разбросе 19.2% и 7.9% — то есть
   неотличим от шума стенда. Дефолт уже упирается в диск.

## 10. Эксперимент 6 — прогретый кеш

Bitmap heap scan, один и тот же диапазон, холодный старт и следом два повтора
без сброса кеша. Рабочий набор ≈460 MB помещается в 4 GB RAM. `exp = 6`
в `data/results.csv`.

| `io_method` | Итерация 1 (холодная) | Итерация 2 | Итерация 3 |
|---|---|---|---|
| `sync`, `eic=16` | 1149 мс | **116 мс** | **110 мс** |
| `worker`, `eic=16` | 1966 мс | **111 мс** | **108 мс** |

На холодном чтении между методами 1.7× разницы, на прогретом — ноль
(110 против 108 мс). Когда рабочий набор в памяти, физического чтения нет,
и прятать асинхронности нечего. Seq scan и VACUUM в этот эксперимент не
включены: 33 GB при 4 GB RAM прогретыми не бывают.

## 11. fio перемерен на файле 12 GB

Причина: сессия 1 снимала профиль на файле 8 GB, который позже оказался
занижающим по последовательному чтению (808 против 1058 MiB/s). Случайное
чтение перемерено на том же 12-гигабайтном файле, что и последовательное.

| Тест | IOPS | MiB/s | avg, мс | p50, мс | p99, мс |
|---|---|---|---|---|---|
| randread 8k QD1 | 4 845 | 37.8 | 0.206 | 0.196 | 0.305 |
| randread 8k QD16 | 60 736 | 474.5 | 0.263 | 0.255 | 0.391 |
| seqread 128k QD16 | 8 466 | 1058.2 | 1.889 | 1.876 | 2.146 |

Масштабирование QD1 → QD16 = **×12.5** ценой роста латентности на 28%.
Прежние значения с файла 8 GB: 0.238 мс и ×12.6. Абсолютные величины разъехались
на 15–19%, несущий вывод не изменился. **В статье использовать эти числа**
(0.206 мс, ×12.5, 474 MiB/s) и потолок последовательного чтения 1058 MiB/s —
все они сняты с одного файла. Сырой вывод: `data/observ/out12-randread8k-qd*.json` и
`data/observ/fio12-seqread128k-qd16.json`.

## 12. Что снято с §0 «упирается в IPC»

Формулировка «`worker` упирается в стоимость IPC» была выводом по исключению.
Альтернатива «конкуренция за блокировку очереди заявок» проверена по
`data/waits.csv`: `LWLock / AioWorkerSubmissionQueue` ловится 1–7 сэмплами
при доле 0.0–0.1% во всех прогонах. Конкуренции за очередь заявок нет.

Что остаётся доказанным: пул не помогает (пул 8 не лучше пула 2–8), воркеры на
своих блокировках не стоят, а бэкенд принимает 5152 пробуждения `epoll_wait`
за прогон (strace, §0). Корректная формулировка — узкое место в самой передаче
работы между процессами, а не в числе воркеров.

## 13. Мелкая фактическая правка

`effective_io_concurrency` появился в PostgreSQL **8.4**, релиз 1 июля 2009 года
([release notes 8.4](https://www.postgresql.org/docs/current/release-8-4.html):
«Allow I/O read-ahead for bitmap index scans (Greg Stark). The amount of read-ahead
is controlled by effective_io_concurrency»). Формулировка «префетч с 2008 года»
неверна — правильно «с версии 8.4».

## 14. Перепроверка release notes 19 перед публикацией

Выполнена 2026-08-11 по
[release-19.html](https://www.postgresql.org/docs/19/release-19.html)
(беты 2, ноты от 16 июля 2026). В разделе «Migration to Version 19» I/O-пунктов
по-прежнему **нет ни одного** — ни `io_method`, ни `io_workers`, ни
`effective_io_concurrency`. Тезис про отказ старта с `io_workers` остаётся в силе.

Побочно: в той же секции значится переименование типа wait event
`BUFFERPIN` → `BUFFER` — к AIO отношения не имеет, но уместно в абзаце про
переучивание мониторинга.

## 15. `pg_stat_io` по трём методам

Пробел прослеживаемости, найденный проверкой существа: врезка в начале файла
обещала §1–§3 как источник для `pg_stat_io`, но самих чисел в тексте не было —
только выгрузки в `data/observ/statio_*.txt`. Восполняю.

Bitmap heap scan, дельта `pg_stat_io` за прогон, строка
`client backend / relation / normal`:

| `io_method` | reads | read_bytes | read_ms | hits |
|---|---|---|---|---|
| `sync` | 58 753 | 488 128 512 | 614.6 | 1 582 |
| `worker` | 58 753 | 488 128 512 | 1 692.7 | 2 509 |
| `io_uring` | 58 753 | 488 128 512 | 840.7 | 861 |

Содержательный вывод, важный для раздела статьи про наблюдаемость: **число
операций и объём одинаковы при всех трёх методах, и все они по-прежнему
числятся за `client backend`.** Различается только `read_ms`. То есть при
переходе на `worker` слепнет `pg_stat_activity` (чтение уезжает в процессы
`io worker`), а `pg_stat_io` продолжает приписывать чтения тому бэкенду,
который их заказал.

## 16. Версионные атрибуции (проверены fact-check, раунд 2)

Четыре утверждения раздела «Что появилось в 17-й, 18-й и 19-й» не выводятся
из измерений и держатся только на источниках. Фиксирую их здесь, чтобы они
были прослеживаемы наравне с числами:

| Утверждение | Источник |
|---|---|
| `io_combine_limit` появился в 17-й, дефолт 128 kB | [docs/17 runtime-config-resource](https://www.postgresql.org/docs/17/runtime-config-resource.html): «The default is 128kB»; [release notes 17](https://www.postgresql.org/docs/17/release-17.html): «Allow the grouping of file system reads with the new system variable io_combine_limit» |
| `io_max_combine_limit` — только в 18-й | на странице docs/17 отсутствует; release notes 18: «with server variables io_combine_limit and io_max_combine_limit added to control it» |
| Read stream в 17-й обслуживал последовательное чтение; на bitmap heap scan и вакуум распространён в 18-й | release notes 17: «including for sequential reads using streaming I/O»; `heapam.c` в `REL_17_STABLE` создаёт поток с `READ_STREAM_SEQUENTIAL`; bitmap — коммит `2b73a8cd33b7`, вакуум — коммит `9256822608f3` от 2025-02-14, оба в цикле 18-й |
| Дефолт `effective_io_concurrency` поднят с 1 до 16 в 18-й | release notes 18, пункт авторства Melanie Plageman |

Отдельно проверено, что утверждение «до 18-й PostgreSQL читал с диска
синхронно» корректно и при наличии read stream в 17-й: в `read_stream.c`
17-й стоит авторская оговорка «If we had real asynchronous I/O we might need
a slightly different definition».
