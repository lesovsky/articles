# pgpro_rp: материалы эксперимента

Полный набор данных к статье [`pgpro-rp.md`](pgpro-rp.md).

## Статус: не публикуется

Статья дописана и проверена, но публиковать её я не стал. По итогам замеров
впечатление от инструмента сложилось как от прототипа, а не от production-ready
решения: приоритизация обходится обычным `SET` и не закрывается правами, не
действует на параллельных воркеров, по умолчанию не работает вовсе, планы живут
внутри отдельной базы и ломают механизм всему кластеру, а факты притормаживания
нигде не фиксируются. Писать обзорный материал с уклоном в сильные стороны о таком
инструменте нечестно, а переделывать его в разбор недоработок — не та задача,
ради которой всё затевалось.

Материалы остаются здесь целиком: измерения воспроизводимы, методика описана, и
если расширение доработают, статью можно будет достать и перемерить. Список
замечаний передан владельцу продукта отдельно.

Вопрос эксперимента: что расширение `pgpro_rp` (приоритизация ресурсов в
Postgres Pro Enterprise) реально делает с нагрузкой — насколько сильно
притормаживает низкоприоритетные сеансы, при каких условиях механизм вообще
включается и где он обходится.

## Стенд

| | |
|---|---|
| СУБД | Postgres Pro Enterprise 18.4 |
| Расширение | `pgpro_rp` 1.4 |
| ОС | Debian 12 |
| CPU / RAM | 4 vCPU, 8 GB |
| Диск | SSD, 100 GB |
| PostgreSQL | `shared_buffers = 1GB`, `max_parallel_workers_per_gather = 2`, `max_worker_processes = 8` |

Машина намеренно маленькая: приоритизация проявляется только при конкуренции за
ресурс, и на четырёх ядрах её проще создать честным способом, чем на большой.

`usage_tracking_interval` — единственный параметр, который меняется по ходу
экспериментов; во всех прогонах, кроме `02-interval.sh` и `07-overhead.sh`, он
равен `1s`.

## Как повторить

Скрипты рассчитаны на каталог `~/rp/scripts/` на стенде и запускаются по порядку.

| Скрипт | Что делает |
|---|---|
| `00-setup.sh` | установка расширения, роли, планы, права |
| `01-dataset.sh` | генерация всех трёх датасетов, включая расширение и планы в базе `oltp` |
| `02-interval.sh` | развёртка `usage_tracking_interval` 0 / 1 / 5 / 60 с на коротком и длинном запросе |
| `02b-interval-ratio.sh` | проверка правила «интервал должен быть меньше длительности запроса» на запросе ≈35 с |
| `02c-query-profile.sh` | зависит ли приоритизация от профиля запроса: сканирование против вычислений |
| `03-noisy-neighbor.sh` | сценарий «шумный сосед»: OLTP против аналитики, три конфигурации |
| `04-daynight.sh` | группы назначений планов и переключение между ними |
| `05-firefight.sh` | понижение приоритета уже выполняющемуся запросу по PID |
| `06-plan-function.sh` | пользовательская функция выбора плана |
| `07-overhead.sh` | цена наблюдения: TPS при разных значениях интервала |
| `08-limits.sh` | границы механизма: параллельные воркеры, обход через `SET`, `RESET`, журнал |
| `09-io-weights.sh` | ось `session_ioread_weight` на датасете больше памяти |
| `10-charts.py` | графики (нужен matplotlib) |
| `lib.sh` | общие функции: замер, фоновая нагрузка, запись CSV |

Все измерения сведены в [`RESULTS.md`](RESULTS.md).

## Грабли стенда

Пять вещей, на которые я потратил время и которые стоит знать, если повторяете.

`ALTER SYSTEM SET shared_preload_libraries = 'a, b'` закавычивает список целиком
и сервер после перезапуска не стартует. Правьте конфиг напрямую или пишите
список без пробелов после запятых.

Фоновая нагрузка обязана самоограничиваться по `statement_timeout`. Оборванный
прогон оставляет сессии, которые доедают все ядра, и машина перестаёт принимать
даже ssh-подключения.

`awk` в русской локали печатает `132,864` вместо `132.864` и ломает CSV — в
скриптах разбора перцентилей стоит `LC_ALL=C`.

Сравниваемые веса нужно мерить одновременно (`pair_query` в `lib.sh`). При
последовательном замере придушенный запрос идёт в разы дольше, фоновая нагрузка
успевает завершиться по `statement_timeout`, и «быстрый» вес меряется уже на
свободной машине — разница получается завышенной в несколько раз.

Активная группа назначений — глобальное состояние кластера. `04-daynight.sh`
её переключает, и если не вернуть обратно, все последующие замеры молча меряют
отсутствие приоритизации. Для этого в `lib.sh` есть `ensure_default_group`.
